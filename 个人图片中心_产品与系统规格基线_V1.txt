==============================================================================
1. 产品定位
==============================================================================
个人图片中心是一个云端图片资产管理、浏览、分享与创作平台。

它覆盖图片完整生命周期：
上传 -> 校验 -> 存储 -> 版本生成 -> 整理 -> 搜索 -> 浏览 -> 下载 -> 分享 -> 创作 -> 回收站 -> 恢复/永久删除。

产品支持四类使用方式：
- 个人：用户管理自己的长期图片资产。
- 家庭：家庭成员共享一个空间，并按角色协作。
- 团队：摄影团队、设计团队、项目组等多人管理图片资产。
- SaaS：未来面向公众注册使用，具备多租户、配额和计费扩展能力。

产品体验参考方向：
- QQ 相册：相册、分享、熟悉的图片组织方式。
- Google Photos：时间线、搜索、智能整理。
- 百度相册/网盘式图片管理：存储、下载、批量管理。
- Apple Photos：沉浸式浏览、回忆、视觉体验。
- 小米相册：移动网页端使用习惯、时间线、地点与相册。

产品差异化：
- 幻灯片是一等公民，不是附属按钮。
- 同一份图片资产可以用多种方式观看和创作。
- 支持多种存储后端，默认 Cloudflare R2，但不把业务层写死到 R2。
- 图片原图、优化图、AI 增强图、编辑版本分离管理。
- 创作系统不是写死模板，而是 Presentation Engine。


==============================================================================
2. 用户与空间模型
==============================================================================
一个账号可以拥有或加入多个空间（Space）。

空间类型：
- Personal：个人空间。
- Family：家庭空间。
- Team：团队空间。

示例：
我的账号
├── 我的个人空间
├── 我的家庭
├── 摄影团队
└── 项目素材空间

每个空间独立拥有：
- 图片资产
- 相册
- 文件夹
- 标签
- 收藏视图
- 幻灯片项目
- Presentation 项目
- 分享链接
- 成员
- 权限
- 存储策略
- AI 设置
- 回收站
- 配额与用量统计
- 操作日志

空间切换必须是顶层能力，用户无需退出登录即可切换。
所有查询、下载、分享、删除、AI 处理、后台任务都必须显式绑定 space_id，避免多租户越权。


==============================================================================
3. 角色与权限模型
==============================================================================
V1 使用四级角色：
- Owner
- Admin
- Editor
- Viewer

默认权限：
Owner：
- 空间全部权限。
- 管理成员。
- 修改空间存储策略。
- 修改配额相关设置。
- 删除空间。
- 转让空间所有权。
- 查看完整审计日志。

Admin：
- 管理成员，但不能转让 Owner。
- 管理图片、相册、分享、创作、标签、文件夹。
- 修改大部分空间设置。
- 不能删除整个空间和转让所有权。

Editor：
- 上传、编辑、删除图片。
- 创建/修改相册。
- 创建幻灯片和 Presentation。
- 创建分享链接。
- 不管理成员和核心空间设置。

Viewer：
- 查看允许访问的图片与相册。
- 默认允许下载优化图。
- 原图下载权限可由空间配置进一步限制。
- 不能上传、编辑、删除、分享、创建内容。

底层实现要求：
- UI 先呈现四个角色。
- 权限系统不能完全写死为 role === "admin" 之类的散落判断。
- 应设计 Permission/Capability 层，为未来细粒度权限预留：
  upload_media、delete_media、download_original、create_share、invite_member、use_ai、manage_storage 等。

4. 认证与账号体系
==============================================================================
支持全部以下登录方式：
1. 邮箱 + 密码。
2. 邮箱验证码 / Magic Link。
3. Google OAuth。
4. GitHub OAuth。
5. Microsoft OAuth。

邮箱 + 密码是基础登录方式，必须始终可用。

账号相关能力：
- 注册。
- 邮箱验证。
- 登录。
- 退出。
- 忘记密码。
- 重置密码。
- 修改密码。
- 绑定/解绑第三方账号。
- 查看登录会话。
- 撤销其他会话。
- 安全邮件通知。

安全原则：
- 密码使用成熟密码哈希算法存储。
- OAuth state/nonce 等按规范处理。
- Magic Link 必须短时有效且一次性使用。
- 登录、注册、验证码、重置密码接口需要 Rate Limit。
- 不在 URL、前端日志、浏览器存储中暴露长期敏感凭据。

==============================================================================
6. 图片上传系统
==============================================================================
V1 为用户手动上传，不做手机自动备份和系统级自动同步。

支持：
- 单张上传。
- 多张批量上传。
- 拖拽上传。
- 选择文件上传。
- URL 导入。
- ZIP 导入作为增强能力，可进入后台任务处理。

默认上传链路采用混合模式：
1. 浏览器向 NestJS API 请求上传会话。
2. API 校验用户、空间、配额、文件元信息。
3. API 返回短期上传凭证/签名信息。
4. 浏览器直接将文件上传至 Cloudflare R2，避免图片流量经过 API 服务器。
5. 上传完成后客户端通知 API，或由后端通过可靠方式确认对象存在。
6. API 创建 MediaAsset、MediaVersion(original) 记录并投递处理任务。
7. Worker 生成优化版本。

上传体验要求：
- 每个文件显示进度。
- 显示等待、上传中、处理、完成、失败状态。
- 批量上传可以继续浏览图库，不强制停留上传页面。
- 失败文件可单独重试。
- 网络中断后支持恢复未完成上传。
- 大文件支持分片/Multipart Upload。
- 并发数根据浏览器和网络情况控制，不能无限并发。


==============================================================================
7. 图片格式与文件校验
==============================================================================
V1 正式支持：
- JPEG/JPG
- PNG
- WebP
- AVIF
- GIF

HEIC/HEIF：
- V1 架构预留。
- 可以作为导入转换增强项，不要求所有部署环境无条件原生展示。

校验要求：
- 不只相信文件扩展名。
- 校验 MIME 与实际文件内容。
- 图片解码失败的文件不得进入正常图库。
- 限制单文件大小，具体额度由 Plan/Space 配额配置。
- 对极端像素尺寸、解压炸弹等异常图片进行保护。
- 原始文件名保留为 metadata，但对象存储 key 不直接使用不受控原文件名。


==============================================================================
8. 图片资产模型
==============================================================================
图片不是“一个文件路径”，而是逻辑资产 MediaAsset。

MediaAsset 表示用户看到的一张图片，包含：
- id
- space_id
- owner/uploader
- original_filename
- mime_type
- width
- height
- aspect_ratio
- file_hash
- perceptual_hash
- captured_at
- uploaded_at
- location
- exif summary
- status
- trash status
- current edit reference

MediaVersion 表示这张图片的实际文件版本：
- original
- thumbnail
- optimized_1280
- optimized_2560
- ai_enhanced
- edited
- future variants

版本记录至少包含：
- media_asset_id
- version_type
- storage_provider
- object_key
- mime_type
- width
- height
- bytes
- checksum
- created_at
- processing metadata

所有相册、故事页、幻灯片默认引用 MediaAsset，而不是复制文件。


==============================================================================
9. 原图与优化图策略
==============================================================================
按空间配置原图策略，并允许单张图片覆盖。

空间策略例：
- keep_original = true
- keep_original = false_after_optimized
- ask_per_asset / allow_override

推荐默认：
Personal：保留原图。
Family：保留原图。
Team：Owner/Admin 可配置。

默认自适应生成：
- thumbnail
- 1280px 浏览版
- 2560px 高清浏览/幻灯片版
- original（按策略保留）

不为每张图片无脑生成所有尺寸和所有格式。
只有需要时再生成附加 AVIF/WebP 或其他尺寸，例如：
- 幻灯片。
- 公开分享。
- 热点图片。
- Presentation。
- 高 DPI/4K。
- 用户主动请求。

浏览页面禁止直接加载原图。


==============================================================================
10. 图片处理 Pipeline
==============================================================================
标准流程：

Upload session
-> R2 original object
-> MediaAsset/MediaVersion database records
-> BullMQ job
-> Media Worker
-> decode / validate
-> EXIF parse
-> thumbnail generation
-> 1280 generation
-> 2560 generation
-> hash / pHash
-> metadata update
-> optional AI jobs
-> ready state

任务必须可重试并具有幂等性。
同一个 job 重跑不能无限创建重复 MediaVersion。
失败时：
- 原图保留。
- 资产状态标记 processing_failed 或部分可用。
- 用户仍可看到上传记录和失败原因。
- 管理后台可重试任务。


==============================================================================
11. 去重与相似图片
==============================================================================
采用两层基础策略：

第一层：精确去重
- SHA-256 或等价强哈希。
- 判断完全相同文件。
- 在空间范围内优先检测。
- 是否允许跨用户/跨空间物理去重应谨慎，V1 不依赖跨租户去重，避免权限与隐私复杂度。

第二层：内容相似
- pHash/感知哈希。
- 识别重新压缩、缩放后的相同或高度相似图片。
- 后续可加入 AI embedding 相似度。

发现重复时不擅自永久删除。
可提供：
- 跳过。
- 保留两张。
- 标记为重复。
- 合并组织关系。
- 将新文件作为已有资产的新版本（仅在规则明确时）。


==============================================================================
12. Folder / Album / Tag / Favorite
==============================================================================
四种组织方式必须区分：

Folder：
- 树形组织。
- 用于用户熟悉的“目录”概念。
- 一个资产在默认语义下有一个主要 Folder 位置。
- 支持移动。

Album：
- 逻辑集合。
- 一张图片可以属于多个 Album。
- 加入 Album 不复制文件。
- Album 可以有封面、描述、排序、背景、默认幻灯片等属性。

Tag：
- 多对多标签。
- 用户标签和 AI 标签应区分来源。
- 用户可修改/删除 AI 标签。

Favorite：
- 用户级收藏状态。
- 在多人 Space 中允许每个成员拥有自己的收藏视图，避免一个人的收藏影响其他成员。

未来 Smart Album：
- 根据日期、标签、人物、地点、收藏等规则动态生成。

13. 搜索与筛选
==============================================================================
V1 先使用 PostgreSQL 能力实现可用搜索，不立即引入复杂搜索集群。

可搜索字段：
- 文件名。
- 相册名。
- 文件夹名。
- 标签。
- OCR 文本。
- AI 描述。
- 拍摄地点文本。
- 基础 EXIF 字段。

筛选：
- 日期范围。
- 上传日期。
- 拍摄日期。
- 文件类型。
- 图片尺寸。
- 收藏。
- 是否有 GPS。
- 是否有原图。
- AI 处理状态。
- 相册/文件夹。

排序：
- 拍摄时间新到旧/旧到新。
- 上传时间。
- 文件名。
- 文件大小。
- 随机。
- 自定义相册排序。

后续预留向量搜索，例如“海边的孩子”“夜晚城市灯光”等自然语言语义搜索。


==============================================================================
14. EXIF、时间与地点
==============================================================================
时间优先级：
1. EXIF captured time。
2. 文件内可可信时间。
3. 上传时间。

用户可以手动修正拍摄时间。
修正后保留原始 metadata，不应破坏原文件。

位置：
- 从 EXIF GPS 读取。
- 无 GPS 时允许手动设置地点。
- 数据库存储标准经纬度和可选地点文本。
- 地图 UI 不绑定单一地图厂商，前端地图 Provider 可替换。

隐私：
- 分享图片时可以选择隐藏位置元数据。
- 公开分享默认不暴露完整 EXIF/GPS，除非用户明确开启。

==============================================================================
18. 幻灯片系统（核心）
==============================================================================
Slideshow 是一级核心产品能力。

数据模型应与 Album 分离：
Album 决定“有哪些图片”；
Slideshow 决定“如何播放”。

一个 Album 可以拥有多个 Slideshow 配置。

默认配置：
- 单张停留 6 秒。
- Cross Fade。
- 转场约 900ms。
- 轻微 Ken Burns。
- 按相册顺序。
- 循环开启。
- 随机关闭。
- 字幕默认关闭。
- 音乐由用户选择。

支持：
- 播放/暂停。
- 上一张/下一张。
- 全屏。
- 循环。
- 随机。
- 停留时长。
- 转场类型。
- 背景。
- 音乐。
- 字幕。
- 日期/地点显示开关。

首批转场：
- Cross Fade
- Fade to Black
- Slide
- Zoom
- Ken Burns
- None

不追求几十种廉价特效。


==============================================================================
19. 幻灯片图片适配与预加载
==============================================================================
图片适配不能全部 object-fit: cover。

推荐智能 Fit：
- 横图、竖图、超宽图根据屏幕比例决定 contain/cover。
- 后续可利用人脸/主体位置减少关键内容被裁剪。
- 竖图在宽屏显示时可使用当前图片的模糊、暗化放大版本作为背景。
- 用户可切换纯黑、纯白、自定义背景图、相册背景。

预加载：
- 当前图片。
- 前 3 张。
- 后 1 张。
- 根据网络和内存动态调节。
- 禁止一进入幻灯片就下载整个相册所有 2560 图。

版本选择：
- 手机优先 1280。
- 普通桌面优先 2560。
- 4K/高 DPI 按需更高版本。
- 原图仅显式请求。


==============================================================================
20. 幻灯片音乐
==============================================================================
音乐由用户自己选择，不根据图片氛围自动生成/推荐。

来源：
- 上传音乐。
- 音乐 URL。
- 用户音乐库中的音乐。
- 多首播放列表。

播放：
- 播放/暂停。
- 上一首/下一首。
- 音量。
- 循环。
- 随机。
- 进度。
- 淡入淡出。
- 切歌 Crossfade 可作为增强。

浏览器自动播放规则：
- 不假设能无交互播放带声音媒体。
- 分享幻灯片可使用“进入相册”入口，用户点击后进入沉浸式播放并启动音乐。

音乐处理：
- 上传后生成网页优化版本。
- 原始音乐是否保留可以后续按空间策略设计。
- 播放默认使用压缩版本。


==============================================================================
21. Presentation Engine
==============================================================================
家庭纪念网页、旅行记录、年度回忆、作品集统一基于 Presentation Engine。

核心不是把内容编译成一坨不可维护 HTML，而是保存结构化 Presentation 数据。

Presentation 包含：
- title
- description
- cover
- theme
- background
- music
- blocks
- share settings
- publish state

首批 Blocks：
- Cover
- Text
- Image
- Gallery
- Slideshow
- Timeline
- Ending

后续：
- Map
- Photo Book
- Quote
- Divider
- 3D Gallery
- Contact/Portfolio block

同一 MediaAsset 可以在多个 Presentation 中引用，不复制 R2 文件。


==============================================================================
22. 家庭纪念网页
==============================================================================
家庭纪念网页是 Presentation 的重要预设之一，而不是独立系统。

创建流程：
1. 从图库/相册选择图片。
2. 选择“创建纪念网页”。
3. 选择预设或空白页面。
4. 设置标题、封面、背景、音乐。
5. 调整图片顺序和区块。
6. 实时预览。
7. 设置分享权限。
8. 发布独立 URL。

默认预设建议：
- 家庭纪念。
- 旅行记录。
- 年度回忆。
- 摄影作品集。

用户可编辑：
- 标题。
- 描述。
- 封面。
- 背景。
- 音乐。
- 文字。
- 图片顺序。
- Slideshow 设置。
- 主题。
- 是否显示日期/地点。

发布页必须适合手机访问。


==============================================================================
23. 时间轴
==============================================================================
时间轴按 captured_at 为主组织，fallback 到 uploaded_at。

层级：
- 年。
- 月。
- 日/事件。

支持快速跳转年份和月份。
大量图片时必须分页/虚拟化，不在前端一次加载整个年度全量大图。
用户修正拍摄时间后，时间轴应即时反映。


==============================================================================
24. 地图
==============================================================================
地图显示含 GPS 的图片。

能力：
- 地图聚合点。
- 缩放后展开局部图片。
- 点击地点查看对应图片集合。
- 可从地图进入相册/幻灯片。
- 用户可手动为图片设置或移除地点。

无 GPS 图片不强制自动猜测。
AI 地点识别只能作为建议，不能覆盖用户真实 EXIF/手动位置。


==============================================================================
25. 相册书、故事、数字画框、3D
==============================================================================
相册书：
- 模拟页式浏览。
- V1 可预留，非第一开发优先级。
- 底层引用 MediaAsset。

故事网页：
- 实际由 Presentation Engine 实现。
- 不再重复建立独立数据模型。

数字画框：
- 直接复用 Slideshow Engine。
- 默认全屏、无控制器、无限循环、随机或顺序播放、长停留时间、自动恢复。
- 适合电视、平板、旧电脑浏览器。

3D 空间：
- 明确属于后续高级能力。
- V1 数据模型和路由不阻塞未来扩展即可。
- 不允许为了 3D 过早引入复杂渲染依赖影响核心图库。


==============================================================================
26. 图片编辑
==============================================================================
采用非破坏式编辑。

允许操作可逐步实现：
- 裁剪。
- 旋转。
- 翻转。
- 亮度。
- 对比度。
- 饱和度。
- 锐化。
- 基础滤镜。

原则：
- 不覆盖 original。
- 编辑结果保存为 edited MediaVersion。
- 编辑参数保留，便于后续重新渲染/撤销。
- 用户可以恢复到原图。
- 多次编辑应避免无限复制超大文件，可设计当前版本与历史策略。


==============================================================================
27. AI 能力
==============================================================================
AI 使用云 API，并通过 Provider Adapter 抽象。

第一批 AI 能力：
- 自动标签。
- 场景识别。
- 图片描述。
- OCR。
- 人脸检测。
- 人脸聚类。
- 相似图片辅助。
- 智能分类建议。

后续：
- AI 增强。
- 超分辨率。
- 去噪。
- 老照片修复。
- 更高级语义搜索。

原则：
- AI 任务异步执行。
- AI 失败不影响普通上传、下载和浏览。
- AI 结果必须带来源/状态。
- 用户可以关闭某类 AI。
- 用户标签优先级高于 AI 自动标签。
- AI 不擅自永久修改 original。


==============================================================================
28. 人脸能力
==============================================================================
V1 推荐先做人脸检测与聚类，不默认自动给人物命名。

流程：
- 检测人脸区域。
- 生成聚类/相似人物集合。
- 用户确认“这是同一个人”。
- 用户手动设置人物名称。

隐私原则：
- 人脸能力默认只在授权空间内使用。
- 分享页默认不公开内部人物聚类信息。
- 不把人物身份推断当作绝对事实。


==============================================================================
29. 下载系统
==============================================================================
支持：
- 下载当前浏览优化版。
- 下载原图（有权限时）。
- 多选下载。
- 整个相册下载。
- Presentation 使用图片的批量导出（可后续）。

小批量：
- 可以直接生成响应或快速 ZIP。

大批量：
- 创建后台 Export Job。
- Worker 流式读取对象并生成 ZIP/归档。
- 结果放入临时对象。
- 返回短期下载 URL。
- 到期自动清理。

禁止：
- 把数 GB 图片一次加载进 API 进程内存。


==============================================================================
30. 分享系统
==============================================================================
分享对象可以是：
- 单张图片。
- Album。
- Slideshow。
- Presentation。

访问方式：
- Public Link。
- Password Protected。
- Login Required。
- 指定成员/用户（后续可增强）。

可配置：
- 有效期。
- 查看次数限制。
- 是否允许下载优化图。
- 是否允许下载原图。
- 是否展示 EXIF。
- 是否展示 GPS。
- 是否允许查看评论（若未来加入）。

分享 Token：
- 使用不可预测随机值。
- 不暴露数据库自增 ID。
- 可随时撤销。


==============================================================================
31. 回收站与分层删除
==============================================================================
采用分层删除 + 回收站。

默认回收站：30 天。
空间管理员未来可调整保留时间。

操作：
- 普通删除 MediaAsset -> 进入回收站。
- 回收站中可恢复。
- 到期后台清理。
- 删除优化版本 -> 可重新生成。
- 删除原图 -> 强二次确认。
- 永久删除整张资产 -> 再次确认并清理所有关联文件/关系。

恢复时：
- 恢复 Album/Folder 关系应尽可能恢复。
- 若原目录不存在，可恢复到安全默认位置。


==============================================================================
32. Cloudflare R2 与 Storage Adapter
==============================================================================
Cloudflare R2 是默认存储。

业务代码不直接到处写 R2 SDK 调用。
建立 Storage Adapter 接口。

至少抽象：
- createUploadSession
- putObject
- getObject
- getSignedReadUrl
- deleteObject
- headObject
- copy/move
- streamObject
- multipart lifecycle

未来 Provider：
- AWS S3。
- S3 Compatible。
- 自建对象存储。
- 图床。
- 个人网盘。
- 本地同步/电脑端桥接（后续）。

V1 核心链路只要求 R2 真正可用，其他 Provider 先保证扩展边界，不必伪实现。


==============================================================================
33. R2 对象组织与访问控制
==============================================================================
R2 Bucket 默认私有。

对象 key 不使用可猜测用户路径直接暴露。
推荐包含：
- space namespace
- asset id
- version type
- random/immutable key

示意：
spaces/{spaceId}/media/{assetId}/original/{objectId}
spaces/{spaceId}/media/{assetId}/v/1280/{objectId}
spaces/{spaceId}/media/{assetId}/v/2560/{objectId}
spaces/{spaceId}/media/{assetId}/thumb/{objectId}

访问：
- 私有图片通过 API 授权后获得短期签名 URL 或受控代理。
- 公开分享也应经 share 权限层决定可访问版本。
- 不因为拿到某个内部 object key 就永久绕过权限。

==============================================================================
37. 性能基线
==============================================================================
目标空间规模：
至少以 10,000+ 图片空间作为设计基线。

必须：
- 游标分页优先。
- Infinite Scroll。
- 虚拟化 Grid/Masonry。
- 缩略图优先。
- 预知图片尺寸避免 layout shift。
- 查询字段索引。
- CDN/浏览器缓存。
- 前端不一次性拉取全空间 metadata。
- Viewer/Slideshow 只预加载邻近图片。
- 大型 ZIP、AI、压缩任务走后台。

性能不是要求某个虚构毫秒数字，而是保证架构不会因图片数量线性拖垮页面。
后续上线后以真实监控数据制定 SLO。


==============================================================================
38. 缓存与 CDN
==============================================================================
优化图片适合较长缓存，因为 MediaVersion 使用不可变 key 或版本化路径。

缓存原则：
- thumbnail/optimized：immutable URL，长缓存。
- original：受控访问。
- 用户资料、权限等动态数据：短缓存或不缓存。
- 分享页面静态结构可按发布版本缓存，但权限判断不能被缓存绕过。

当 edited/AI version 更新时创建新 version key，避免复杂 CDN purge 作为主流程。


==============================================================================
39. 管理后台
==============================================================================
后台管理与普通图库 UI 分离。

Admin 主要能力：
- 用户管理。
- Space 管理。
- 存储占用。
- 配额。
- 上传异常。
- BullMQ 任务。
- 失败媒体处理。
- AI 调用与失败。
- 分享链接审计。
- 系统日志。
- 存储 Provider 状态。
- Redis/PostgreSQL/Worker 健康状态。
- 封禁/限制滥用账户。
- Plan/Quota 配置（即使 V1 暂不收费）。

后台不是用户默认首页。

配额策略可控制：

==============================================================================
42. 安全基线
==============================================================================
必须考虑：
- 多租户越权。
- IDOR。
- CSRF（视认证方式）。
- XSS。
- SSRF（URL 导入重点）。
- 上传恶意文件。
- MIME 欺骗。
- Rate Limit。
- 暴力登录。
- 签名 URL 泄露。
- 分享 Token 枚举。
- 权限缓存错误。
- 管理后台权限提升。
- 日志中泄露敏感数据。

URL 导入：
- 禁止访问本机、内网、metadata service 等保留地址。
- 限制重定向。
- 校验响应类型和大小。
- 设超时。

审计日志记录关键变更，但不记录密码、Token、OAuth secret、完整签名 URL。

48. V1 核心验收闭环
==============================================================================
至少通过以下真实用户流程：

流程 A：个人用户
1. 注册账号。
2. 创建个人空间。
3. 上传 100 张真实图片。
4. 浏览器直传 R2。
5. 后台生成缩略图和优化图。
6. 用户在 Grid/Masonry 中浏览。
7. 打开 Viewer。
8. 下载优化图和原图。
9. 删除图片到回收站并恢复。

流程 B：家庭
1. 创建 Family Space。
2. 邀请成员。
3. 设置 Admin/Editor/Viewer。
4. Editor 上传图片。
5. Viewer 只能执行允许操作。
6. 权限越权请求被 API 拒绝。

流程 C：幻灯片
1. 创建 Album。
2. 创建 Slideshow。
3. 调整顺序、转场、背景、音乐。
4. 手机与桌面播放。
5. 分享密码链接。
6. 外部访客输入密码后正常播放。

流程 D：纪念网页
1. 选择图库图片。
2. 创建家庭纪念 Presentation。
3. 加入 Cover/Text/Gallery/Slideshow/Timeline。
4. 设置音乐和背景。
5. 发布。
6. 获得独立 URL。
7. 手机访问正常。

流程 E：故障
1. 某张图片处理失败。
2. 原图仍存在。
3. UI 显示失败状态。
4. Admin/Worker 可重试。
5. 重试不会产生无限重复版本。

51. 任务类型与重试策略
==============================================================================
任务需要区分可自动重试与需要人工介入。

可自动重试：
- R2 短暂读写失败。
- AI API 429/5xx。
- 网络型 URL 导入超时（有限次数）。
- 图片衍生版本写入失败。

不应无限自动重试：
- 图片内容损坏。
- 不支持格式。
- 用户权限已撤销。
- 配额不足。
- URL 明确被 SSRF 拒绝。

每个 Job 必须保存：
- 可读错误码。
- 最后错误。
- attempts。
- next retry / dead-letter 状态。
- 对应 asset/share/export id。

==============================================================================
53. 数据与备份
==============================================================================
PostgreSQL 是元数据核心，需要定期备份。
R2 是媒体文件核心。

灾备原则：
- 数据库备份和媒体存储分别考虑。
- 恢复时 MediaAsset 与 MediaVersion 能重新关联。
- 优化版本可再生，原图不可轻易再生，因此原图的灾备优先级更高。
- 数据库迁移使用版本化 migration。
- 不在生产环境直接手工改 schema 作为正常流程。

后续可增加跨区域/跨 Provider 备份策略。


==============================================================================
54. 设计原则冻结
==============================================================================
1. 图片是界面视觉主体。
2. 普通用户不先看到后台管理。
3. 高级设置逐层展开，默认界面保持简洁。
4. 幻灯片是一等公民。
5. 同一图片资产被多场景引用，不复制文件。
6. 原图永不被普通编辑覆盖。
7. AI 永远是增强层，不应让核心图库依赖 AI 才能工作。
8. 存储 Provider 可替换。
9. 大任务异步。
10. 私有资源默认私有。
11. 分享是授权视图，不是把 Bucket 改成公开。
12. 第一版先把图片做好，不被视频和 3D 拖垮。

附录 B：MediaAsset 生命周期状态机
==============================================================================
MediaAsset 不应该只有“有/没有”两个状态。建议至少区分：

uploading：
客户端正在将原始对象上传 R2，此时还不能视为完整图片资产。

uploaded：
原始对象已经确认存在，数据库已创建资产，但衍生图尚未完成。

processing：
Worker 正在解析 EXIF、生成缩略图、1280、2560 等版本。

ready：
最低可用版本已经完成，可以正常进入图库、Viewer 和 Slideshow。

partial_ready：
部分版本可用，但一个或多个非关键衍生任务失败。例如 1280 已完成、2560 失败。
用户可以正常浏览，同时后台或管理员可重试失败任务。

processing_failed：
关键解码或处理失败。必须保留失败原因，不允许 UI 假装上传成功。

trashed：
资产进入回收站。普通图库查询默认排除。

purging：
执行永久删除中。此时禁止恢复和新建引用。

purged：
数据库完成最终清理；若采用物理删除后不保留记录，也可仅在 AuditLog 中留痕。

重要约束：
- UI“上传成功”与“图片完全处理完成”是两回事。
- uploaded 后可以先展示本地/原图临时预览或 processing 占位，但不能把未完成状态伪装成 ready。
- 后台重试必须从数据库检查现有 MediaVersion，避免重复产物。
- 资产进入 trashed 后，已有公开分享应立即失效或根据明确策略隐藏该图片，不能继续通过旧 URL 无限制访问。


==============================================================================
附录 C：上传会话状态机
==============================================================================
UploadSession 推荐状态：

created
-> uploading
-> uploaded
-> verifying
-> committed
-> expired / failed / cancelled

created：
API 已验证权限和配额，生成上传会话。

uploading：
一个或多个分片正在上传。

uploaded：
客户端认为所有分片完成，但服务端尚未最终确认。

verifying：
API/后台通过 HeadObject、checksum、size 等确认 R2 对象真实存在并符合声明。

committed：
成功创建 MediaAsset 和 original MediaVersion，并投递处理任务。

expired：
上传会话过期。未完成 multipart 需要后台清理。

failed：
服务端确认失败。

cancelled：
用户主动取消。

防止“幽灵图片”：
只有 committed 以后才进入正式图库数据。
对于 R2 中存在但数据库没有 committed 的孤儿对象，后台清理任务按 TTL 回收。


==============================================================================
附录 D：分享访问决策顺序
==============================================================================
任何分享请求都按固定顺序判断，避免不同 Controller 出现不同逻辑：

1. ShareLink 是否存在。
2. 是否被 revoked。
3. target 是否仍存在且未永久删除。
4. 是否超过 expires_at。
5. 是否超过 max_views（若配置）。
6. 是否要求登录。
7. 是否限制特定成员/用户。
8. 是否需要密码。
9. 密码是否已经通过当前短期分享会话验证。
10. 当前请求是否被允许查看目标资源。
11. 当前请求是否允许下载 optimized。
12. 当前请求是否允许下载 original。
13. 是否允许展示 EXIF。
14. 是否允许展示 GPS。

分享密码不能以明文保存。
通过密码以后应建立短时 share session，而不是把密码反复放在 URL 中。

附录 E：图库查询契约
==============================================================================
图库查询不返回无限列表。

推荐请求语义：

GET /spaces/:spaceId/media?cursor=...&limit=...&sort=...&view=...

响应至少包含：
items
nextCursor
hasMore
query metadata

每个 item 返回列表所需最小字段：
id
thumbnail URL 或可请求标识
width
height
captured_at
favorite state
processing state
selection-relevant flags

列表接口默认不返回：
完整 EXIF
全部标签详细对象
全部 MediaVersion
原图签名 URL
AI 大文本
审计日志

详情按需加载，避免 10,000 张图片列表响应膨胀。

附录 F：批量操作规范
==============================================================================
批量操作分为即时操作和后台任务。

适合即时：
- 收藏/取消收藏。
- 添加标签。
- 加入 Album。
- 轻量移动 Folder。

适合后台：
- 大规模 ZIP 导出。
- 批量 AI。
- 批量重新生成优化版本。
- 存储迁移。
- 大批量永久删除。

批量任务 UI：
- 显示已选数量。
- 提交后生成 job。
- 用户可以离开页面。
- 顶部/通知中心可查看进度。
- 失败时显示“成功多少、失败多少”而不是只显示一个笼统失败。
- 对可重试项目提供重试。


==============================================================================
附录 G：图片编辑版本规则
==============================================================================
用户对同一 MediaAsset 编辑时：

Original：
不可被普通编辑覆盖。

Edit Recipe：
保存裁剪框、旋转角度、曝光、对比度等可重放参数。

Edited Version：
由 recipe 渲染出的实际浏览文件。

Current Display Version：
用户可选择当前默认显示 Original/Edited/AI Enhanced 中的某个可展示版本。

当用户“恢复原图”：
- 不删除历史 edit。
- 将 current display 指针恢复。
- 用户可选择稍后清理不再需要的 edit versions。

这样可以避免编辑后永远失去原始照片。


==============================================================================
附录 H：AI 数据与人工数据优先级
==============================================================================
同一个概念可能同时存在三类数据：

1. Original Metadata：EXIF/原文件提供。
2. AI Suggested Metadata：AI 提议。
3. User Confirmed Metadata：用户确认/修改。

优先级：
User Confirmed > Original factual metadata（视字段）> AI Suggested。

例如地点：
- EXIF GPS 是事实来源。
- AI 说“可能在东京”只是建议。
- 用户手动改为“京都”后，以用户设置为产品展示结果。

例如人物：
- AI 聚类只给 cluster。
- 用户命名后才成为“妈妈”“小明”等人物名称。

任何 AI Provider 更新模型都不能静默覆盖用户确认结果。


==============================================================================
附录 I：前端页面状态规范
==============================================================================
不是写一句“所有页面要有 Loading”，而是规定核心页面具体状态。

图库：
- initial_loading：首次加载骨架。
- populated：正常图片。
- empty_new_space：新空间无图，显示上传引导。
- empty_filtered：有图库但筛选无结果，提供清除筛选。
- offline/retryable_error：网络失败可重试。
- permission_denied：明确没有权限，不伪装成空列表。

Album：
- 空 Album 显示“添加图片”而不是错误。
- Album 中部分图片 trashed 时不显示坏图；编辑者可看到缺失提示。

Viewer：
- 当前 2560 加载失败时降级到 1280。
- 1280 失败但 original 可读时可选择进一步降级。
- 当前图片被删除时从 Viewer 序列移除并提示。

Slideshow：
- 某张图失败则跳过并记录，不能中断整个播放。
- 音乐加载失败时幻灯片继续运行并显示非阻断提示。
- 页面进入后台时根据浏览器策略暂停/继续，行为需一致。

分享：
- 已过期、已撤销、密码错误、无权限必须是不同状态。
- 不使用统一“404”掩盖所有情况，除非安全策略明确需要。


==============================================================================
附录 J：数据一致性关键规则
==============================================================================
1. 数据库记录 committed 前必须确认 R2 original 对象存在。
2. 数据库删除 MediaVersion 与 R2 删除对象需要通过可重试任务协调，不能假设跨系统事务。
3. 永久删除采用“标记 purging -> 删除对象 -> 删除/归档关系 -> 完成”的补偿式流程。
4. 生成新版本时优先写对象成功后再写数据库引用。
5. 若对象成功写入、数据库失败，记录孤儿对象并由清理任务处理。
6. AlbumItem、PresentationBlock、Slideshow 对 trashed asset 的行为必须统一。
7. Space 被删除必须进入专门的异步销毁流程，不能一个 HTTP 请求同步删除全部图片。
8. Owner 转让需要事务保证 Space 始终存在一个 Owner。
9. 最后一位 Owner 不能直接退出 Space。
10. OAuth 账号解绑前必须确保用户仍有至少一种可登录方式。

附录 L：备份与恢复优先级
==============================================================================
P0：PostgreSQL 元数据与用户/权限/Space 关系。
P0：用户选择保留的 Original。
P1：Edited 与 AI Enhanced 中用户明确保留的重要版本。
P2：optimized_1280 / optimized_2560。
P3：thumbnail。

原因：
P2/P3 可从原图重新生成。
如果成本受限，灾备优先保护不可再生数据，而不是复制所有缓存型衍生图。

恢复演练必须验证：
- Space 与权限关系恢复。
- MediaAsset 能找到 original。
- 缺失 thumbnail 能重新生成。
- 分享链接在恢复后仍遵循权限与过期规则。


==============================================================================
附录 M：下游 AI Coding Agent 的硬约束
==============================================================================
后续生成 Cursor/Claude Code 指令时必须包含：

1. 不允许擅自把 NestJS 改成 Next.js API Routes 单体后端。
2. 不允许把 PostgreSQL 改成 SQLite 作为生产默认。
3. 不允许把图片 Base64 存数据库。
4. 不允许把 R2 Bucket 设成全公开以“简化访问”。
5. 不允许在 API 进程同步完成大型图片压缩。
6. 不允许用 thumbnail 代替原图下载。
7. 不允许 Album 加图时复制图片文件。
8. 不允许编辑覆盖 original。
9. 不允许 Presentation 把每张图复制一份。
10. 不允许为完成 Demo 删除 Space/RBAC 多租户模型。
11. 不允许把 AI 变成上传成功的前置依赖。
12. 不允许先实现视频、3D 等非核心功能而核心上传/图库/幻灯片仍是假功能。
13. 每个 Phase 必须有真实可执行验收。
14. 发现现有仓库已经实现相同能力时先检查再修改，不无理由重写。
15. 生成代码后必须运行类型检查、单元测试/集成测试和关键流程验证。
